# Послідовні етапи для окремих п'ятигодинних вікон

Виконуйте етапи по черзі. Кожен промпт самодостатній: перевірте фактичний стан репозиторію перед змінами, дотримуйтеся `SPEC.md` і `DESIGN.md`, не оголошуйте вимогу виконаною без перевірки. Наприкінці кожного етапу запишіть перевірені результати у `PROGRESS.md`. Жоден етап не повинен лишати рішення таким, що не збирається.

## Етап 1. MVC і модель (ціль: до 4 годин)

У корені цього репозиторію створіть ASP.NET Core MVC застосунок .NET 8 з EF Core SQLite. Реалізуйте `Organizer`, `Venue`, `Event` зі зв'язками та URL зображення події. Додайте migrations, демонстраційні дані й повні Razor CRUD сторінки трьох сутностей. Валідуйте введення, явно позначте час UTC, забороніть видаляти місце чи організатора з подіями, захистіть POST від CSRF. Створіть зрозумілу українську навігацію та каталог. Перевірте збірку, створення бази й основні HTTP сценарії. Це C1. Не починайте наступний етап, поки збірка не зелена.

## Етап 2. JSON API (ціль: до 4 годин)

Виходячи зі збірного результату етапу 1, додайте CRUD JSON endpoints для організаторів, місць і подій, що використовують ту саму базу й валідацію. Поверніть коректні `200/201/204/400/404/409`, не віддавайте внутрішні винятки. Для списку подій підтримайте `skip`, `limit` і абсолютний `nextLink`; встановіть верхню межу `limit`. Додайте автоматизовані API тести та колекцію запитів для демонстрації. За можливості додайте кешування тільки списку з інвалідацією після зміни. Перевірте CRUD і межі пагінації. Це C5, B1, QA1 і, лише після доказу, B9.

## Етап 3. Публічні сторінки й пошук (ціль: до 4 годин)

На основі етапу 2 зробіть окремий адаптивний Bootstrap landing page для кожної події: фото, опис, дата, місце, організатор і постійно видимий спосіб зв'язку. Додайте коректні title, description, canonical, Open Graph, robots і sitemap; запишіть справжній результат SEO-аудиту після публікації, не вигадуйте показники. У формі події замініть вибір місця на autocomplete із серверним пошуком після 3 символів та невеликою debounce-затримкою. Перевірте клавіатуру, мобільну ширину й порожні стани. Це C6, C7 і F2.

## Етап 4. Мапа і сторонній API (ціль: до 4 годин)

Від результату етапу 3 покажіть усі місця з подіями на інтерактивній мапі OpenStreetMap через сумісну бібліотеку. Додайте фільтр за категорією та датою, який змінює набір точок, і діаграму кількості подій за категоріями, пов'язану з фільтром. Для події покажіть прогноз за координатами через погодний API лише коли його часовий горизонт містить дату; явно обробіть недоступність мережі. Не видавайте одну статичну точку за інтеграцію. Це C8, F1 і B2 після живої перевірки.

## Етап 5. Живі оновлення (ціль: до 5 годин)

Від результату етапу 4 додайте статус події (`заплановано`, `перенесено`, `скасовано`) та живе оновлення каталогу через ASP.NET Core SignalR. Запишіть порівняння WebSockets, Server Sent Events і Long Polling на однаковому сценарії: затримка доставки, число запитів та обсяг трафіку; збережіть сирі виміри й умови тесту. Порівняння мусить бути відтворюваним. Це C10 і C11; не зараховуйте C10 тільки за наявність SignalR.

## Етап 6. Якість і поставка (ціль: до 4 годин)

Від результату етапу 5 додайте Dockerfile і Compose з постійним томом SQLite, health endpoint та наскрізні тести створення, редагування, перегляду й фільтрації. Зберіть і запустіть контейнер, виконайте тести й зафіксуйте виміряне покриття сценаріїв. Налаштуйте CI збірку й тести. Опублікуйте весь код у Git-репозиторії. Це C4 і QA2 після окремих доказів; збірка образу без запуску Compose не завершує C4.

## Етап 7. Доступ і хмара (ціль: до 5 годин)

Від результату етапу 6 захистіть усі MVC та API операції запису за допомогою OAuth2 провайдера, який відповідає C16, і перевірте заборону запису для гостя. Після реальної авторизації й тестів розгорніть застосунок у хмарі з постійним сховищем бази та секретами поза Git. Додайте CD після оновлення `main`, перевірте фактичний новий реліз і проведіть зовнішній SEO-аудит публічної сторінки. Це C16, QA3, C2, C3 та завершення C7 лише після окремих доказів. Якщо немає доступу до провайдера або хмари, зафіксуйте точну межу і не заявляйте ці вимоги виконаними.

## Після основної поставки

Якщо лишається час у наступному вікні, розгляньте редактор Markdown C12/F3/C13/C14 або окремий SPA F5. Це новий обсяг робіт: спочатку впишіть точний контракт і тестовий сценарій у `SPEC.md`. Не імітуйте повноту цих вимог частковим UI.
